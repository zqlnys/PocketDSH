# Tier D 能力清单

这份文件说的每一件事都有对应的测试；数字是本地实测的，不是估计。

**最后核对：2026-11-27，版本 0.1.20261127 (990)。**

## 这些证据是在哪测的

**105 条 iOS 测试跑在 iOS 模拟器上（Apple Silicon 的 CI runner），跑的是同一份源码、为真机构建。**

**它证明了什么：**解释器、musl 加载器、系统调用层和文件系统在 Darwin 上、在 app 沙盒里、以 arm64 真正执行了，而不只是编译通过。

**它没有证明什么：**真机上的行为。模拟器和真机共用内核，但内存压力、看门狗和 JIT 限制的表观不同——**E2 不需要 JIT，也不需要 `fork()`，这两条限制对它不成立；但真机上还没跑过。**

**要补上这一块，**需要在有签名的真机上跑同一套测试。这里没有签名证书，所以这条限制是真的，不是疏忽。

## 能用

| 能力 | 证据 |
| --- | --- |
| busybox 全套 applet | 384 条差分用例与 qemu 逐字一致（1 条已知差异，见下） |
| CPython 3.12 + 标准库 | 30 个模块的广度探针、13 行窄探针，输出与 qemu 逐字一致 |
| `fork` / `exec` / `wait4` | 一个进程里 fork + wait 100 次；`subprocess` 可运行；失败的 `exec` 返回 `ENOENT`，过长的参数返回 `E2BIG` |

| 真实休眠 | `time.sleep(0.25)` 真的等 250 ms，与 qemu 一致 |
| 取消正在跑的命令 | 每 65536 条指令检查一次，300 ms 内停下 |
| 写入上限 | 运行期 64 MB `RLIMIT_FSIZE`，超出时写失败 |
| 内存上限 | `E2_HEAP_MB` 同时约束 `brk` 与 `mmap`，超出抛 `MemoryError` |
| 工作区挂载 | guest 的 `/workspace` 就是项目目录 |
| **持久会话** | `E2_SESSION=1` 时一个 guest shell 跨多条命令存活，`cd` 和变量都保持。命令由写线程分次喂入，shell 阻塞在 read 上等着——不是轮询。完成标记走 `E2_SESSION_MARK` 指向的独立文件，输出里没有分帧痕迹 |
| **`asyncio` 事件循环** | `sleep`、`gather`、`Queue`、`run_until_complete` 都可用——它需要的 socketpair 自管道现在能收发。**TCP 服务端不行**，因为没有东西能 `connect`（见「没有网络」） |
| **`/proc` 已种入** | `df`、`free`、`uname -a`、`nproc` 都能用；`/proc/mounts` 与 `statfs` 一致；`/proc` 与 `/proc/self` 都从可写目录提供，因为设备上的 rootfs 只读 |

| **27 个系统调用** | `tools/syscall-probe.py` 逐行与 qemu 对比：`getpid`、`stat`、`symlink`、`hardlink`、`chmod`、`listdir`、`walk`、`pipe`、`select`、`lseek`、`getcwd`、`time` 等 |

## 这些模块可导入

```
ssl  hashlib  bz2  lzma  sqlite3  pyexpat  decimal
xml.etree.ElementTree  curses  curses.panel
```

**`gdbm` 不行**——缺的是 Python 侧的模块（裁剪时去掉了），不是共享库。构建脚本会报告这件事，不会静默跳过。

**`PYTHONPYCACHEPREFIX` 故意不传给 guest**：指向可写前缀会让 Python 重新编译标准库并写出结果，而包里已有的预编译字节码反而不用。实测 `import asyncio` 是 155 秒对 24 秒。

## 已知错误

| 症状 | 影响 |
| --- | --- |
| **`awk` 的 `"cmd" | getline` 和 `system()` 不工作** | 两者都经 `popen`，它要 `clone(CLONE_VM\|CLONE_VFORK\|SIGCHLD, stack)`——非 NULL 的栈让这条路径被当作线程，返回 `EINVAL`，于是 `system()` 返回 -1、`getline` 拿到空串。`vfork` 系统调用（58）已实现为 fork，但 busybox 走的是 clone。**试过把 `CLONE_VM\|CLONE_VFORK` 当 fork 处理，进程在内核态死掉——比原来更糟，已撤回。** qemu 正常 |

| 症状 | 影响 |
| --- | --- |
| **`pow()`、`math.hypot()`、`math.log2()` 结果错误** | 误差是常数 `+0.0223674`。**十轮的定位结论**：`log2` 确实在执行；归约结果 `d7 = 1.0` 精确；`fmov d2, #-1.0` 精确；`ubfx` 的索引（40）与编码一致；从 `.rodata` 读到的表项 `0.9922480467550775` 与 E2 加载的值**完全一致**——也就是说 **E2 的内存读取本身没错**，而 `1.0` 出现在表内另一个位置（`0x9B540`，对应索引 73，超出 6 位字段范围）。**结论：我对这张表布局的理解是错的，问题不在已排除的那些指令上。** 已排除：加减乘除、比较、`sqrt`、`exp2`、`log`、`log10`、`log1p`、`exp`、`frexp`、`ldexp`、`floor`、`trunc`、`int()`、双↔单精度转换、`ubfx`、64 位逻辑立即数、`fmov` 立即数与寄存器形式、`fmadd` |

## 已知错误

| 症状 | 影响 |
| --- | --- |
| **`LANG=C` 且没有 `LC_ALL` 时，长参数被截断** | **精确边界：9 个字符及以下的参数完好，10 个及以上被截成 2 个字符。** `python3.12 - /aaaaaaaaa` 得到 `arg1 9`，而 `/aaaaaaaaaa` 得到 `arg1 2`。同样的长度在 `LANG=C.UTF-8` 下完全正常（`arg1 11`）。**已缓解**：`LC_ALL` 现在真的会透传到 guest（此前桥接层设了它、harness 没透传，等于空操作）。**已排除**：harness 传给 guest 的 argv 是完整的（`[argv] 1` 追踪可见）；`mbrtowc` 在 C locale 下经 ctypes 实测正确（`setlocale` → "C"，`MB_CUR_MAX` → 1，每字节返回长度 1）；关闭 `PYTHONCOERCECLOCALE` 不改变结果；`sys.argv[0]` 在两种 locale 下都是 1 个字符，但那是 `python3 -` 的正常行为，不是缺陷。**四轮之后停止追查**——缓解措施有效，触发条件是用户显式 `unset LC_ALL` 再 `export LANG=C`，继续投入的回报低于成本 |
| **`pow()`、`math.hypot()`、`math.log2()` 结果错误** |
| 限制 | 原因 |
| --- | --- |
| **没有网络** | 只支持 `socketpair`，没有任何会 `connect` 的东西。**`ssl` 能导入、CA 证书齐全，但发不出 HTTPS 请求。** |
| **`socket.socketpair` 可以收发数据** | `sendto`(206)、`recvfrom`(207)、`sendmsg`(211)、`recvmsg`(212) 都已实现，往返数据通过。**`SCM_RIGHTS`（传描述符）仍不支持，带控制消息的调用返回 `ENOTSUP`——明说而不是悄悄丢掉** |
| **没有线程** | 见下 |
| **`run_linux` 还没有用上会话模式** | 会话在 harness 和桥接两层都已工作（`e2_bridge_session_start/_write/_wait/_close`），但 `run_linux` 仍每次启动新 guest。把它接上是下一步 |

| **`time.gmtime()` 对小值算错** | `gmtime(0)` 给出 `1969-12-31 48:00`，`gmtime(3600)` 给出 `01:00` 变成 `25:00`，`gmtime(86400)` 的日期差一天；`gmtime(1700000000)` 正确。**Python 层的 `//` 和 `%` 已验证正确**，所以问题在 musl 的 `gmtime_r`。后果：`strftime` 抛 `ValueError: hour out of range`。**边界在 2^30**，`t ≥ 2^30` 完全正确，小于时有两处固定偏移：`tm_hour` **恒多 24**，`tm_wday` **恒少 1**（模 7），而 `tm_mday`、`tm_yday`、分、秒都正确。**`datetime.datetime.fromtimestamp` 因此抛 `ValueError: hour must be in 0..23`。**

**已排除（都测过）：**整数 `//` 和 `%` 与 qemu 一致；`SMULH`/`UMULH`（编译器「除以常量」的手法）七条检查全过；`strftime`/`gmtime` 的调用本身正常。

**原始结构体（`ctypes` 直接调 `gmtime_r`，九个字段）给出了最强的证据：**

```
t=100   E2   [40, 1, 24, 1, 0, 70, 10, 0, 0]
        qemu [40, 1,  0, 1, 0, 70,  4, 0, 0]
t=2e9   E2   [20, 33, 3, 18, 4, 133, 3, 137, 0]
        qemu [20, 33, 3, 18, 4, 133, 3, 137, 0]
```

**只有 `tm_hour`（+24）和 `tm_wday`（+6）不同，其余七项逐字节相同。**注意 `tm_yday` 在两边都是 0——**它是「年内第几天」的零基值，没有被一起带偏**，所以不是「整体日期偏了一天」。

**一个错误的符号比较能同时解释这两处。**`tm_hour` 多 24 就是 `remsecs` 多了整整 86400 秒，而这正是 musl 里 `if (secs < 0) secs += 86400;` 那一行做的事；`days = (t - secs) / 86400` 因此少 1，`tm_wday = (days + 4) % 7` 就少 1（模 7）。**一行误判、两个字段、方向和量都对得上。**

**边界不是 2^30**：`t = 2^30-1` 和 `2^30` 都正确，而 `2^29`、`7e8` 错误 —— **是值依赖的，不是量级阈值。**

**已排除的第五项：C 层的除法与取模本身。**通过 `imaxdiv` 直接调用，`t=100`、`6399`、`12800`、`66880`、`67712`、`1e6`、`2e9` 的商与余数都与 qemu 逐项一致。**所以送进计算的输入是对的，而结果的两个字段是错的。**

**反汇编 `gmtime_r` 把位置定下来了。**它调 `0x64f9c`（即 `__secs_to_tm`），而后者在 `0x64ff8` 处是：

```
tbnz x2, #0x3f, 0x65130      ; 测试余数的第 63 位 —— 就是 secs < 0 那个判断
```

**这条指令若把第 63 位当成第 31 位来测，两个字段的偏移就完全对得上。**E2 的 `TBZ`/`TBNZ` 解码（`bit_pos = (BIT(31) << 5) | BITS(23,19)`）看起来是对的，**但我手算的编码把测试跑挂了——`pc` 没有前进，说明那三条根本没被识别成 TBZ，所以是编码算错而不是解码错。测试已撤回，不留下没验证的东西。**

**测过了，`TBZ`/`TBNZ` 的第 63 位与第 31 位区分正确**（六条单指令检查，编码来自汇编器而不是手算）。**这是第六项排除。**

**顺带一条编码上的事实：`tbnz x2, #31` 和 `tbnz w2, #31` 汇编出同一条指令**（`0x37F80042`）——位号小于 32 时 b5 为 0，两种写法没有区别。

**小时的算法本身已验证正确**：libc 用 `msub`（求余）→ `umull 0x91a2b3c5` → `lsr #43`（除以 3600），这三条按序列测过十二组，全部正确。

**所以问题在更前面——算商 `x0` 的那三条：**

```
smulh x0, x2, x0
asr   x0, x0, #13
sub   x0, x0, x2, asr #63     ← 带移位寄存器的 SUB
```

**`x0` 是 `t / 86400`；它错了，余数就错，小时就错。**下一步该测的是**带移位操作数的 `SUB`**（`sub xD, xN, xM, asr #63`）这种形式。
| **`prlimit64` 只报告不执行** | 设置新的 rlimit 会被接受但忽略 |
| **符号链接的绝对目标不工作** | `/tmp/link -> /tmp/target` 这样的链接，`open` 会返回 `ENOENT`：目标是按**宿主**路径解析的，不经过 guest 映射。**相对目标正常**。这是真限制，不是回归 |
| **exec 最多携带 32 个参数和 64 个环境变量** | 超过时返回 `E2BIG`（真内核的上限高得多）。上限受限于每次 exec 的栈上缓冲区；`run_proc` 是嵌套的，把它调大会把栈风险换成一个更少见的错误 |

## 关于线程

`clone` 能创建执行流，但跨执行流的 pc 会损坏——故障转储里出现过 `pc=0x872ca4`，即 `0x400000872ca4` 的高 32 位丢失，且不在任何映射里。

**这一点试过十一轮，其中四次得出了自己造成的错误结论**（继承的指令计数、错误的采样点、逐指令的区域扫描、bash 的 `sigsuspend`）。**目前关闭，记录在 `docs/persistent-session.md`。**

**CPython 的 `threading` 依赖它，所以 `threading` 不可用。**

## 性能

**构建机上（`-O2`，`perf-check`）：**

```
合成循环       49–52 ns/指令
真实负载       74–77 ns/指令（CPython 启动，3910 万条指令）
```

**设备上（Release，iOS 模拟器，实测单测耗时）：**

```
import asyncio          25.4 秒   （-Os 构建时是 68.0 秒）
python3 -c 'pass' 级别   3.2–7.2 秒
```

**这两个是不同的问题，之前混在一起：构建机上的数字一直是 `-O2`，而设备上跑的是 `-Os`，差 2.8 倍。现在两处都是 `-O2`，CI 会守住它。**

**分发不是瓶颈**：Python 负载上每条指令只有 2.0 次守卫比较（加前门判别前是 33.6 次）。剩下的差距是缓存行为。

**真实负载那个数才是该盯的**——合成循环测的是分发，而分发早就不是成本所在。

**测量的噪声底：单次采样 75–81 ns（约 8%）；`perf-check` 现在跑五次取最小值，降到 74–77 ns（约 4%）。**比这更小的改动用这个脚本分辨不出来——本次会话有三次优化落在这个区间内，其中包括一个四项区域缓存（读数 75–76 对 73，已撤回）。**指令数是确定的，所以多次运行之间的差异是机器的，取最小值把这个差异压掉。**

**已经测过并否决的方向**（都在 4% 分辨率内，或没有效果）：

| 方向 | 结果 |
| --- | --- |
| 四项区域缓存 | 75–76 对 73，在噪声内 |
| 区域查找改二分 | 12 次采集中位数约 75，与线性扫描相同 |
| `-O3`、`-fno-plt` | 与 `-O2` 完全相同 |
| `PYTHONPYCACHEPREFIX` 透传 | 24 秒 → 155 秒，反而更慢 |

**二分那条说明单项命中缓存已经让查找足够罕见——查找不是成本所在。**

**真正的那个数量级来自别处：`-Os` → `-O2` 是 2.8 倍（68 秒 → 24 秒）。**在这之前，所有微优化都在一个被 2.8 倍掩盖的区间里测量。**

**剩下的差距是结构性的**：3910 万条指令、74–77 ns/条，而原生只要约 30 ms。**要跨过它需要译码缓存或线程化分发这一类改动，不是改一行。**
