# Tier D 能力清单

这份文件说的每一件事都有对应的测试；数字是本地实测的，不是估计。

**最后核对：2026-11-28，版本 0.1.20261128 (1060)。**

## 这些证据是在哪测的

**105 条 iOS 测试跑在 iOS 模拟器上（Apple Silicon 的 CI runner），跑的是同一份源码、为真机构建。**

**它证明了什么：**解释器、musl 加载器、系统调用层和文件系统在 Darwin 上、在 app 沙盒里、以 arm64 真正执行了，而不只是编译通过。

**它没有证明什么：**真机上的行为。模拟器和真机共用内核，但内存压力、看门狗和 JIT 限制的表观不同——**E2 不需要 JIT，也不需要 `fork()`，这两条限制对它不成立；但真机上还没跑过。**

**要补上这一块，**需要在有签名的真机上跑同一套测试。这里没有签名证书，所以这条限制是真的，不是疏忽。

**已排除（都测过）：**整数 `//` 和 `%` 与 qemu 一致；`SMULH`/`UMULH`（编译器「除以常量」的手法）七条检查全过；`strftime`/`gmtime` 的调用本身正常。

**原始结构体（`ctypes` 直接调 `gmtime_r`，九个字段）给出了最强的证据：**

```
t=100   E2   [40, 1, 24, 1, 0, 70, 10, 0, 0]
        qemu [40, 1,  0, 1, 0, 70,  4, 0, 0]
t=2e9   E2   [20, 33, 3, 18, 4, 133, 3, 137, 0]
        qemu [20, 33, 3, 18, 4, 133, 3, 137, 0]
```

**只有 `tm_hour`（+24）和 `tm_wday`（+6）不同，其余七项逐字节相同。**注意 `tm_yday` 在两边都是 0——**它是「年内第几天」的零基值，没有被一起带偏**，所以不是「整体日期偏了一天」。

**一个错误的符号比较能同时解释这两处。**`tm_hour` 多 24 就是 `remsecs` 多了整整 86400 秒，而这正是 musl 里 `if (secs < 0) secs += 86400;` 那一行做的事；`days = (t - secs) / 86400` 因此少 1，`tm_wday = (days + 4) % 7` 就少 1（模 7）。**一行误判、两个字段、方向和量都对得上。**

**边界不是 2^30**：`t = 2^30-1` 和 `2^30` 都正确，而 `2^29`、`7e8` 错误 —— **是值依赖的，不是量级阈值。**

**已排除的第五项：C 层的除法与取模本身。**通过 `imaxdiv` 直接调用，`t=100`、`6399`、`12800`、`66880`、`67712`、`1e6`、`2e9` 的商与余数都与 qemu 逐项一致。**所以送进计算的输入是对的，而结果的两个字段是错的。**

**反汇编 `gmtime_r` 把位置定下来了。**它调 `0x64f9c`（即 `__secs_to_tm`），而后者在 `0x64ff8` 处是：

```
tbnz x2, #0x3f, 0x65130      ; 测试余数的第 63 位 —— 就是 secs < 0 那个判断
```

**这条指令若把第 63 位当成第 31 位来测，两个字段的偏移就完全对得上。**E2 的 `TBZ`/`TBNZ` 解码（`bit_pos = (BIT(31) << 5) | BITS(23,19)`）看起来是对的，**但我手算的编码把测试跑挂了——`pc` 没有前进，说明那三条根本没被识别成 TBZ，所以是编码算错而不是解码错。测试已撤回，不留下没验证的东西。**

**测过了，`TBZ`/`TBNZ` 的第 63 位与第 31 位区分正确**（六条单指令检查，编码来自汇编器而不是手算）。**这是第六项排除。**

**顺带一条编码上的事实：`tbnz x2, #31` 和 `tbnz w2, #31` 汇编出同一条指令**（`0x37F80042`）——位号小于 32 时 b5 为 0，两种写法没有区别。

**小时的算法本身已验证正确**：libc 用 `msub`（求余）→ `umull 0x91a2b3c5` → `lsr #43`（除以 3600），这三条按序列测过十二组，全部正确。

**所以问题在更前面——算商 `x0` 的那三条：**

```
smulh x0, x2, x0
asr   x0, x0, #13
sub   x0, x0, x2, asr #63     ← 带移位寄存器的 SUB
```

**`x0` 是 `t / 86400`；它错了，余数就错，小时就错。**下一步该测的是**带移位操作数的 `SUB`**（`sub xD, xN, xM, asr #63`）这种形式。
| **`datetime.datetime` 的前三个字段恒为零** | **位置参数也一样**——不是关键字参数的问题，上一轮记错了。规律很精确：`datetime(2020,1,1,5,6,7)` 得到年 0、月 0、日 0，而时 5、分 6、秒 7 **正确**。`datetime.date(2020,5,6)` 三个参数**全对**。后果：`fromtimestamp(ts, timezone.utc)` 抛 `ValueError: fromutc: dt.tzinfo is not self`（它拿到的 tzinfo 是 `None`）。**其它 C 层关键字（`sorted`、`int`、`str.split`、`round`、`pow`、`bytes.hex`）都正常**

**调用形式已排除**：位置参数、star-args、`__new__` 直接调用、以及把类绑定到别的名字再调用，四种都给全零。而 `datetime.time`、`datetime.timedelta`、`datetime.date` 都正常。**所以问题在 `datetime.datetime` 的构造函数内部，与调用约定无关**

**再往下排除一层**：`_datetime.datetime.__new__(C.datetime, 2021, 7, 15, 11, 22, 33, 0, None)` 也得到 `0000-00-00T11:22:33`，**所以不是 `datetime.py` 的 Python 包装，是 C 模块里 `new_datetime_ex2` 这一层**。同时 `d.ctime()` 输出里有乱码字符，`d.replace(year=2022)` 抛异常

**参数确实被收到了**：给年、月、日或时传字符串，五种情况都正确抛 `TypeError`，与 qemu 一致。**所以不是「参数没传进来」，是校验之后、存进去之前变成了零。**`date` 也走同一个 `check_date_fields`，而它是对的 |

**所有构造入口都是零**，`now()`、`utcnow()`、`fromordinal()`、`strptime()`、`combine()`、`fromisoformat()` 无一例外，且都保留时、分。**所以不是某一个调用点的问题。**

**「超过八个参数的调用放错栈参数」这个假设已被测掉**：`ctypes` 调 `libc.snprintf` 传十一个参数，其中三个走栈，输出与 qemu 逐字一致。

**所以位置仍在 `new_datetime_ex2` 内部，但不在调用约定上。**

**原始字节把范围收死了**（`d.__reduce__()` 返回的 `data[]`）：

```
E2:    b'\x00\x00\x00\x00\x0b\x16!\x00\x00\x00'
qemu:  b'\x07\xe5\x07\x0f\x0b\x16!\x00\x00\x00'
```

**前四个字节（年高低位、月、日）是零，从第五个起（时、分、秒）完全正确。**`date` 走同一个 `check_date_fields` 且结果正确，所以值不是在校验里丢的，是在这四次字节写入之前或之中丢的 |
| **`math.log2()` 差一个固定常数，`pow()` 因此全错** | `log2(2.0)` 得 `1.0223674090047083`、`log2(4.0)` 得 `2.0223…`、`log2(0.5)` 得 `-0.9776…`——**恒差 `δ = 0.0223674090047083`**，`log2(1.0)` 精确。musl 的 `pow` 走它，所以 `pow(2,2)` 得 `-1.537…`。**`log`、`log10`、`exp`、`exp2`、`log1p` 全部正确**；`hypot` 的 `nan` 是另一回事（见上）。**十三轮排查后仍未修复**，但排除了：Python 层算术、`SMULH`/`UMULH`、C 层除法、`TBZ`/`TBNZ` 位选择、`fmov` 位模式传递、64 位逻辑立即数、`movz`/`movk` 拼常数、**范围归约（用库里真实编码逐条验证：归约结果精确是 1.0，表索引都是 0x31）**。**表项 `0x9b330 = 0.9922480467550775` 已读出**，多项式在 `d2 = -0.00775` 上却返回正值。**22 条单指令测试是这段排查的产物**。**这三个已加进差分套件的已知差异列表（现在共 4 条），每次运行都会比对**——一条修好时会以「不再是差异」的形式自己报出来。

**试过把这 34 条指令的多项式按真实编码整段跑一遍来定位，但那个测试只跑指令、不检查结果——跑通什么也不证明，已移除。**要做成真的，得把表值装进 `d0`–`d19`、把指数项装进 `d1`、再断言 `d0`，而这需要先确认每条 `ldp`/`ldr` 的装载顺序，容易再次写出一个「看起来在测、实际没测」的东西。 |

**这个形状说明范围归约之后拿到的小数项是个常数**——`log2(2.0)` 归约后应为 1.0、小数项为 0，实测却有 δ。**所以不是多项式系数错，是归约出来的 `x` 恒定偏了。**

**反推与位级对照：**由 δ 解出归约后的 `x ≈ 1.1123651085582433`，即 `0x3ff1cc3f5b27819e`，而正确值是 `0x3ff0000000000000`。

**`libm.log2` 经 ctypes 直接调用也是同样错的值**，所以问题在 musl 里，不在 CPython 的包装。

**两个最常见的解释都被实测排除：**

```
正确相加       0x3ff0000000000000
丢了低 32 进位  0x3ff0000000000000   ← 恰好进位 1，高半 +1 后仍是 0x3ff0
实测           0x3ff1cc3f5b27819e
```

**所以不是「加法退化成 32 位」这类简单形态。**

**范围归约已被逐条验证为正确**，用从库里读出的真实编码：`mov` 常数、`add`、`ubfx`、`and`、`sub` 五条，对 2.0、4.0、0.5 三个输入，归约后都精确得到 `1.0`、表索引都是 `0x31`。**六条单指令测试，全过。**

**所以问题在归约之后。**表项本身也读出来了：索引 `0x31` 对应 `0x9b330`，值是 `0.9922480467550775`，于是多项式在 `d2 = d6 - 1.0 = -0.00775` 上求值——**一个负数**。

**而结果给出 `1.0223`，即多项式贡献了 **`+0.0223`**。**符号是正的，而负数参数上的 log 修正项应当是负的。**所以下一步该找的是多项式里那处符号，而不是还原或查表。**

**那处矛盾已经解开：`FMSUB` 的定义是 `Ra - Rn*Rm`，不是 `Rn*Rm - Ra`。**我当初按「先乘后减加数」去读手册，方向反了——**被减数是加数**，所以合并成一次运算时符号落在乘积上，正是当前代码的做法。

**判据是 awk 的取余**：`7 % 3` 在 qemu 上是 `1`，而 `7 - 2*3 = 1`。awk 用一条融合运算算它，所以真实语义是 `z - x*y`；若按 `x*y - z` 则得 `-1`，不成立。**两条观察在这一点上一致，代码是对的，我的第一次改动是错的，已撤回。**`log`、`log10`、`exp`、`exp2`、`log1p` **全部正确**。因为 musl 的 `pow` 走 `exp2(y·log2(x))`，`pow(2,2)` 得到 `-1.537…` 而不是 4。**`hypot` 的 `nan` 是另一回事**（见上） |
| **`prlimit64` 只报告不执行** | 设置新的 rlimit 会被接受但忽略 |
| **符号链接的绝对目标不工作** | `/tmp/link -> /tmp/target` 这样的链接，`open` 会返回 `ENOENT`：目标是按**宿主**路径解析的，不经过 guest 映射。**相对目标正常**。这是真限制，不是回归 |
| **exec 最多携带 32 个参数和 64 个环境变量** | 超过时返回 `E2BIG`（真内核的上限高得多）。上限受限于每次 exec 的栈上缓冲区；`run_proc` 是嵌套的，把它调大会把栈风险换成一个更少见的错误 |

## 关于线程

`clone` 能创建执行流，但跨执行流的 pc 会损坏——故障转储里出现过 `pc=0x872ca4`，即 `0x400000872ca4` 的高 32 位丢失，且不在任何映射里。

**这一点试过十一轮，其中四次得出了自己造成的错误结论**（继承的指令计数、错误的采样点、逐指令的区域扫描、bash 的 `sigsuspend`）。**目前关闭，记录在 `docs/persistent-session.md`。**

**CPython 的 `threading` 依赖它，所以 `threading` 不可用。**

## 性能

**构建机上（`-O2`，`perf-check`）：**

```
合成循环       49–52 ns/指令
真实负载       74–77 ns/指令（CPython 启动，3910 万条指令）
```

**设备上（Release，iOS 模拟器，实测单测耗时）：**

```
import asyncio          25.4 秒   （-Os 构建时是 68.0 秒）
python3 -c 'pass' 级别   3.2–7.2 秒
```

**这两个是不同的问题，之前混在一起：构建机上的数字一直是 `-O2`，而设备上跑的是 `-Os`，差 2.8 倍。现在两处都是 `-O2`，CI 会守住它。**

**分发不是瓶颈**：Python 负载上每条指令只有 2.0 次守卫比较（加前门判别前是 33.6 次）。剩下的差距是缓存行为。

**真实负载那个数才是该盯的**——合成循环测的是分发，而分发早就不是成本所在。

**测量的噪声底：单次采样 75–81 ns（约 8%）；`perf-check` 现在跑五次取最小值，降到 74–77 ns（约 4%）。**比这更小的改动用这个脚本分辨不出来——本次会话有三次优化落在这个区间内，其中包括一个四项区域缓存（读数 75–76 对 73，已撤回）。**指令数是确定的，所以多次运行之间的差异是机器的，取最小值把这个差异压掉。**

**已经测过并否决的方向**（都在 4% 分辨率内，或没有效果）：

| 方向 | 结果 |
| --- | --- |
| 四项区域缓存 | 75–76 对 73，在噪声内 |
| 区域查找改二分 | 12 次采集中位数约 75，与线性扫描相同 |
| `-O3`、`-fno-plt` | 与 `-O2` 完全相同 |
| `PYTHONPYCACHEPREFIX` 透传 | 24 秒 → 155 秒，反而更慢 |

**二分那条说明单项命中缓存已经让查找足够罕见——查找不是成本所在。**

**真正的那个数量级来自别处：`-Os` → `-O2` 是 2.8 倍（68 秒 → 24 秒）。**在这之前，所有微优化都在一个被 2.8 倍掩盖的区间里测量。**

**剩下的差距是结构性的**：3910 万条指令、74–77 ns/条，而原生只要约 30 ms。**要跨过它需要译码缓存或线程化分发这一类改动，不是改一行。**

## 已知差异

差分对比里有一条长期存在的已知差异，记录在 `tools/diff-test.sh` 的注释里；其余 384 条与 qemu 完全一致。
